# Plan: Activity History Persistence and Digest View

> Created: 2026-05-07
> Scope: Medium (multi-phase, 3 phases, ~10 files changed)
> Status: Draft

## Summary

Add durable activity persistence via an append-only `activity.jsonl` log file, then surface that history as an activity digest in the task detail panel and as an enhanced timeline view in the instances tab. Turns ephemeral terminal output into an audit trail that survives restarts and accumulates across sessions.

## Assumptions

> ⚠️ **Flag: ActivityEvent/ActivityEventType relocation.** The plan proposes moving `ActivityEvent` and `ActivityEventType` from `src/views/instances/state.rs` to a shared `src/activity/types.rs`. This is a refactor of existing types — all existing references must be updated. Confidence: 90% that this is the right call (avoids circular deps, enables reuse across instances + tasks). Alternative considered: keep types in place and import from widget code (messy cross-module dep).

> ⚠️ **Flag: JSONL vs JSON array.** The plan uses JSONL (append-only, one event per line). Confidence: 95%. JSONL avoids rewriting the whole file on each event. The only cost is O(n) read on startup — negligible for <10K events.

## Architecture Decisions

- **Decision:** Activity events persist to a separate `activity.jsonl` file alongside `state.json`.
  - **Reasoning:** `state.json` is rewritten on every save — an append-only file avoids write amplification. Separate file means activity history isn't coupled to state.json schema versioning. If `state.json` gets corrupted, activity history survives.
  - **Alternatives considered:** (1) Keep events in `state.json` — lost on state.json rewrite, schema coupling. (2) Keep events in-memory only — lost on restart (current state, defeats the purpose).

- **Decision:** Events are keyed by `pane_id` (UUID) in the JSONL log, not by working directory or task.
  - **Reasoning:** An `InstancePane` UUID is unique and stable for the lifetime of a pane. Task-to-instance linking is via `task.instance_id: Option<Uuid>` — the join is straightforward. Keying by working directory would be lossy (multiple panes in same dir).
  - **Alternatives considered:** Key by task ID — but activity is generated by panes, not tasks. A task might not have an instance_id yet.

- **Decision:** The in-memory `VecDeque<ActivityEvent>` on `InstancePane` stays as the fast path. The JSONL file is loaded on startup and events are merged into the VecDeque.
  - **Reasoning:** The VecDeque already has 500-event cap and 7-day retention. No need to replace it — just extend it. On each `add_activity_event()`, we both push to VecDeque AND append to JSONL. On startup, we load JSONL events that were persisted from prior sessions.
  - **Note:** Closed panes whose events still exist in the JSONL file will NOT be loaded into any VecDeque (the pane no longer exists). This is acceptable — events for closed panes persist in the file but aren't loaded into memory. If a task references a closed pane's UUID, the digest can query the JSONL file directly for those events.

- **Decision:** Activity digest in the task detail panel queries the in-memory VecDeque for the task's associated instance, falling back to the JSONL file for closed instances.
  - **Reasoning:** Most of the time, the instance is still open (user is looking at the task while the agent is running). The in-memory path is instant. For historical tasks where the instance is closed, we read from the file — an acceptable latency for a "what happened" view.

## Out of Scope

- **Migration of existing `state.json` activity events into `activity.jsonl`** — Events already serialized in `state.json` will remain there (with `#[serde(default)]` they're harmless). New events go into `activity.jsonl`. A future cleanup pass could migrate them, but it's not needed for correctness.
- **Activity event deduplication** — The same terminal output could fire the same regex detection multiple times. This existed before this plan and is not addressed here.
- **Activity events for closed instances** — The JSONL file stores them but they're not loaded into VecDeque memory. Querying historical events for a task whose instance is closed is Phase 2's scope, but Phase 2 currently queries the JSONL file lazily. A future enhancement could cache recent closed-instance events.
- **Activity export** — No CSV, JSON dump, or other export format. KISS.
- **`ActivitySummary.format_as_text()` / `format_as_summary_line()`** — These `#[allow(dead_code)]` methods are not used by the UI and are not modified by this plan.
- **Test files** — The codebase doesn't have test harness infrastructure (no test module in lib.rs beyond the unsafe_code check). Don't introduce test frameworks the user hasn't chosen.

## Risk Flags

| Risk | Impact | Mitigation |
|------|--------|------------|
| `activity.jsonl` grows unbounded | Disk growth, slow startup reads | `prune_events()` in Phase 1 applies the same 500/7-day cap as the in-memory VecDeque. Could add a rotation mechanism later. |
| File I/O in `add_activity_event()` on every PTY output | Performance regression | Each `append_event` is a single `write_all` + `flush`. For terminal output this is negligible (~1 write per event, events are rate-limited by regex matching in `detect_and_log_activity`). If it becomes an issue, batch writes on a timer. |
| Moving types from `instances/state.rs` to `activity/types.rs` breaks existing imports | Compile errors | Re-export from `instances/state.rs` with `pub use crate::activity::types::*` — all existing imports keep working. |
| `details_panel.rs` needs access to `InstanceState` from focus view | New coupling between views | The focus view already imports `app.instances` (it gets the `instance_pane` for the terminal). Adding events to the digest follows the same pattern — no new coupling beyond what exists. |
